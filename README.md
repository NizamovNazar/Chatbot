# OA Smart Assistant — V22

Помічник НаУОА українською та англійською: React 18/Vite, Express, MiniSearch + офлайн LSA, офіційний корпус, FAQ, модерація, аналітика та звіти. Зовнішні моделі використовуються за наявності ключів; без них доступні локальні відповіді й витяги з джерел. Розклад залишається явно позначеною демонстраційною моделлю.

Результати й обмеження: [STABILIZATION_V22_REPORT.md](STABILIZATION_V22_REPORT.md). Попередній аудит: [PRE_RELEASE_AUDIT_V21.md](PRE_RELEASE_AUDIT_V21.md).

## Локальний запуск

Потрібен **Node.js 24.22.3 або новіший 24.x**, npm і залежності обох пакетів. Версію зафіксовано в `.node-version`. На цьому Windows-комп’ютері підготовлений переносний Node у `.tools/node-v24.22.3-win-x64`; npm-скрипти й лаунчер підхоплюють його автоматично. Він і `node_modules` не входять у Git. На іншому комп’ютері спочатку встановіть відповідний Node.

Після чистого отримання коду:

```powershell
cd C:\chatbot\server
npm ci
cd ..\web
npm ci
```

На наявному комп’ютері не перезаписуйте `server/.env`. Для нового оточення створіть його на основі `server/.env.example` з власними адміністративними реквізитами. Backend/CLI запускаються з `server` і читають `.env` цієї директорії. Не передавайте секрети через `VITE_*`.

```powershell
cd C:\chatbot\server
npm run dev
```

В іншому терміналі:

```powershell
cd C:\chatbot\web
npm run dev
```

Чат: `http://localhost:5173/`, адмінпанель: `http://localhost:5173/admin.html`, backend: порт 5000. Наявний `launcher.ps1` також підтримується. Для зібраного сайту достатньо одного backend:

```powershell
cd C:\chatbot\web
$env:VITE_API_BASE='/'
npm run build
cd ..\server
npm start
```

Сайт і `/admin.html` тоді доступні на порту backend. `/api/health` перевіряє процес; `/api/ready` — доступність SQL, налаштовану авторизацію та непорожній пошук. Production має працювати через HTTPS; для локальної перевірки production через HTTP задайте точний локальний `CORS_ORIGINS`.

## Сховища та первинний SQL-запуск

Без `DATABASE_URL` використовується `server/data`. Відсутні приватні колекції отримують початкові значення; пошкоджений JSON зупиняє запуск і зберігається для діагностики. Порожній корпус не готовий до відповідей. `npm run index` збирає публічні сторінки. Це робоча команда зі зміною корпусу й резервуванням, не smoke-тест.

З `DATABASE_URL` джерелом істини є PostgreSQL. V22 **не імпортує автоматично** локальні FAQ, чати чи звіти. Існуюча V13-база з маркером міграції продовжує читатися; для нового демо потрібна окрема порожня база.

Команди нижче виконує власник, лише перевіривши, що `DATABASE_URL` вказує саме на нову базу:

```powershell
cd C:\chatbot\server
npm run sql:bootstrap -- --confirm-empty-database
npm run sql:status
npm start
```

Bootstrap обходить офіційні сайти в окремій публічній staging-директорії, очищує/індексує корпус, створює `server/sql/001_postgres.sql` і наповнює знання. Приватні колекції початково порожні. Альтернатива: `npm run sql:bootstrap -- --confirm-empty-database --corpus=C:\public-corpus\docs.json` із перевіреним публічним корпусом. Повторний запуск із маркером не дублює записи; зайнята база без маркера відхиляється. DDL — `CREATE ... IF NOT EXISTS`; звичайний сервер його не виконує. Повтор CLI все ще готує staging-корпус перед перевіркою маркера.

Жоден bootstrap у робочу БД під час V22 не запускався. Реальна SQL-інтеграція потребує окремого тесту. Для хмарної БД налаштуйте TLS за документацією провайдера; DDL-права потрібні окремому bootstrap-власнику.

## Адміністративний доступ

Production вимагає email і пароль 12–256 символів із щонайменше трьома класами та шістьма різними символами або коректний scrypt-хеш. Development підтримує попередню локальну конфігурацію. Чинний пароль автоматично не змінюється.

Для міграції виконайте `npm run auth:hash` в інтерактивному терміналі. Введення приховане, файли не змінюються. Збережіть отриманий `ADMIN_PASSWORD_HASH` як приватний секрет, перевірте вхід після перезапуску, після цього приберіть plaintext `ADMIN_PASSWORD` із production-конфігурації. Хеш має пріоритет і теж не підлягає публікації.

Сесія типово триває 8 годин; logout відкликає токен. Токен лише в React-пам’яті; пароль очищується після входу/401. Перезапуск відкликає RAM-сесії. Невдалі входи обліковуються за IP й акаунтом у SQL або атомарному `admin_auth_v22.json`; блокування переживає перезапуск. Недоступність сховища повертає 503. HTTP 429 містить `Retry-After`. Повторна авторизація для скидання статистики має ті самі ліміти.

Production без SQL потребує **одного процесу**, постійного тому та `AUTH_FILE_PERSISTENT=1`. Файловий лічильник не є міжпроцесним. Для кількох інстансів потрібне додаткове узгодження сесій, стану й лімітів. `TRUST_PROXY=1` дозволяйте лише за одним довіреним reverse proxy із закритим прямим доступом до Node. `CORS_ORIGINS` — точні origins без wildcard.

## Знання, відповіді та аналітика

- `npm run refresh` оновлює 15 офіційних URL, зберігаючи решту корпусу; `npm run index` робить повний обхід. У SQL-режимі команди отримують актуальний корпус із SQL і записують результат у SQL. Сервер підхоплює ревізію кожні 5 секунд без перезапуску.
- `node ../scripts/run-node.mjs scripts/rebuild-knowledge.mjs` — dry-run; `--apply` явно застосовує міграцію. `scripts/build-semantic-index.mjs` перебудовує офлайн LSA без платних embeddings. Обидва читають спільну конфігурацію й підтримують SQL.
- `verified_local` — детермінована відповідь з перевіркою текстової опори. Ручні FAQ мають окрему категорію `faq`/curated. Це не гарантія істинності кожного факту; актуальність джерел потребує контролю.
- Номери `[N]` спільні для URL у промпті й показаному списку. Невідомі числові маркери прибираються; семантичну правильність цитати це не доводить.
- PUT FAQ без `enabled` зберігає попередній стан. Успішне збереження передує публікації нового RAM-стану.
- Типи відповідей спільні для журналу, фільтрів і CSV. Fallback рахується за маршрутом/причиною; no-context включає локальні відповіді. Дати — Europe/Kyiv із DST; невалідні дати відхиляються.
- Випадковий ID діалогу не ідентифікує людину. Старі записи без ID збережені й показані як невизначені. Середнє рахується за відомими діалогами. API/HTML/DOCX використовують спільну модель висновків; старі збережені звіти автоматично не переписуються.

## Моделі та бюджет

Порядок задає `AI_PROVIDERS`, провайдери без ключів пропускаються. Наявні ідентифікатори моделей у шаблоні не перевірялись живими AI-викликами під час V22. Доступність і безкоштовність залежать від акаунта. OpenRouter допускає лише `:free`; заборону платного білінгу інших провайдерів налаштовує власник.

`AI_MAX_CONCURRENT=2` обмежує паралельні ланцюжки одного процесу. `AI_DAILY_ATTEMPTS=40` — постійний ліміт **усіх upstream-спроб**, включно з резервними, за добу Europe/Kyiv. Це межа запитів, а не грошова оцінка чи квота провайдера. Вичерпання дає локальний fallback. Стан бюджету зберігається окремо; недоступність сховища не дозволяє необмежені AI-запити.

## Відтворювані перевірки

```powershell
cd C:\chatbot\server
npm test
cd ..\web
npm run build
cd ..\server
node ../scripts/run-node.mjs scripts/browser-smoke.mjs
```

Тести ізольовані, дані синтетичні, AI-відповіді підставні. Wrapper прибирає робочий URL БД, паролі й API-ключі. Браузерний тест потребує Chrome/Edge/Chromium (`OA_BROWSER_PATH` за потреби), перевіряє production-збірку, пише синтетичні артефакти в `.launcher/v22-browser`. В обмеженому Windows runner може знадобитися `OA_BROWSER_NO_SANDBOX=1` лише для цього тестового браузера.

Реальна PostgreSQL, **лише окрема тестова база**:

```powershell
# Окремий приватний термінал. Ніколи не підставляйте робочий URL.
$env:OA_TEST_DATABASE_URL='postgresql://TEST_USER:TEST_PASSWORD@localhost:5432/oa_test'
$env:OA_PG_TEST_CONFIRM='ISOLATED_DATABASE'
npm test -- src/postgres.v22.integration.test.js
```

Тест відмовляється від робочої БД, створює випадкові власні схеми та прибирає тільки їх. Покриває bootstrap/CRUD/звіти/аналітику/restart/rollback/reconnect/логічне відновлення. Без URL — **SKIP**, не успішна SQL-інтеграція. Реальний outage сервера/мережі й provider-level backup/restore перевіряються додатково на тестовому хостингу. URL із секретом не додавайте до Git або звітів.

Перед релізом додайте до Git усі потрібні нові модулі, `shared/`, `scripts/`, SQL і тести; перевірте чистий checkout. Виключені `.env`, `server/data`, приватні архіви, `.tools`, `node_modules`, `.launcher`. V22 не виконувала commit, push або деплой. До публічного тесту потрібні сильний секрет, постійне сховище, перевірена тестова SQL-база, HTTPS/reverse proxy та резервне копіювання.
